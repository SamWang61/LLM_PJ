## 1. 專題定位與名稱

### 1.1 專題基底

- 舊系統：2025 亮點士林第 3 組 MuscleCore 運動用品電商網站。
- 本次作法：承接其品牌、畫面邏輯、商品與後台操作概念，但以 Python 自行重寫。
- 不直接照搬舊 JS／React／Node.js 原始碼，避免授權、相依套件及技術債問題。

### 1.2 建議命名架構

目前可採「母品牌＋AI 模組」方式，兼顧舊站辨識度與新專題亮點：

| 層級 | 建議名稱 | 定位 |
|---|---|---|
| 系統母品牌 | **MuscleCore** | 運動用品智慧購物網站 |
| 消費者 AI 模組 | **VibeCart AI** | 個人化商品推薦與推薦理由 |
| 管理者 AI 模組 | **VibeInsight AI** | 銷售、庫存及顧客行為洞察 |
| 專題完整名稱 | **MuscleCore｜Hybrid AI 智慧運動商城** | Python＋MongoDB＋Local AI＋Cloud LLM |

建議口號：

> **同一個電商後台，用 Local AI 找得準，用 Cloud LLM 說得懂、看得深。**

### 1.3 尚待全組定案

若全組希望延用先前二選一方案，仍可投票：

- `VibeCart AI｜懂你想買，更懂怎麼賣。`
- `InsightCart AI｜從每一次點擊，看見下一步商機。`

但就目前已有 MuscleCore 程式與視覺成果而言，建議保留 MuscleCore 作母品牌，VibeCart／VibeInsight 作功能模組，較不必再為命名重做專案外殼。

## 4. Hybrid AI 雙路線設計

### 4.1 三層實作策略

| 層級 | 功能 | 技術 | 目的 |
|---|---|---|---|
| Baseline | 基準推薦與基本營運提示 | 本機規則式演算法 | API／模型失效時仍可 Demo，並作比較基準 |
| Local AI | 商品語意向量、Top-N 相似推薦 | Hugging Face BGE Small＋Cosine Similarity | 展示本機模型、低單次成本及資料控制 |
| Cloud LLM | 推薦理由、營運摘要、自然語言問答 | LLM API | 展示大型模型的生成、推理與文字表達能力 |

### 4.2 為何不購買 GPU 仍可完成

- Local 端只執行小型 Embedding 模型，不執行 7B／14B 大型生成模型。
- 商品向量可預先計算並存入 MongoDB，網站查詢時只做相似度計算。
- Cloud LLM 透過 API 使用，不需由組員購置顯卡。
- API 無法使用時，規則式 Baseline 可維持主流程，不讓整場 Demo 跟著 API 一起安詳離場。

### 4.3 Demo 必須記錄的比較數據

| 指標 | Baseline | Local AI | Cloud LLM |
|---|---|---|---|
| 任務完成度 | 推薦／提示 | 語意推薦 | 摘要／問答／理由 |
| 回應時間 | 必測 | 必測 | 必測 |
| 是否依賴網路 | 否 | 模型下載後否 | 是 |
| 單次 API 成本 | 0 | 0 | 依服務計費 |
| 資料是否外送 | 否 | 否 | 是，需先彙總與去識別化 |
| 輸出可解釋性 | 規則清楚 | 相似度分數 | 自然語言解釋，但需防幻覺 |
| 失效備援 | 本身即備援 | 回退 Baseline | 回退本機營運提示 |

## 5. MongoDB 資料庫整合結果

### 5.1 兩個版本必須分清楚

| 層級 | Collections 數 | 用途 |
|---|---:|---|
| 今日可執行 MVP | 4 | 先讓登入、商品、訂單、行為與推薦流程跑通 |
| 完整資料庫藍圖 | 14 | 支援正式商品關聯、購物流程、推薦紀錄、Embedding、AI 對話與營運分析 |

目前 MVP 使用：

```text
users
products
orders
behavior_events
```

完整藍圖定為：

```text
users
categories
products
product_tags
carts
cart_items
orders
order_items
user_events
recommendations
ai_conversations
daily_product_metrics
product_embeddings
ai_insights
```

> 原先附件列出前 12 個 Collections；今日為支援 Local AI 與 Cloud LLM 的模型版本、向量及洞察留存，追加 `product_embeddings` 與 `ai_insights`，形成 14 個完整 Collections。

### 5.2 14 個 Collections 用途

| Collection | 主要用途 | MVP 優先級 |
|---|---|:---:|
| `users` | 會員、管理員、角色、偏好 | Must |
| `categories` | 商品分類與顯示順序 | Must |
| `products` | 商品、價格、庫存、狀態、描述 | Must |
| `product_tags` | 商品標籤與推薦條件 | Should |
| `carts` | 使用者購物車主檔 | Should |
| `cart_items` | 購物車商品與數量 | Should |
| `orders` | 訂單主檔、金額、狀態 | Must |
| `order_items` | 訂單明細與交易當時價格 | Must |
| `user_events` | 瀏覽、點擊、收藏、加購、購買 | Must |
| `recommendations` | 推薦結果、分數、原因、模型版本 | Must |
| `ai_conversations` | AI 問答與對話紀錄 | Should |
| `daily_product_metrics` | 商品每日瀏覽、銷售、轉換統計 | Should |
| `product_embeddings` | 商品向量、Embedding 模型與版本 | Must（Local AI） |
| `ai_insights` | LLM 營運摘要、建議、輸入摘要與模型資訊 | Must（Cloud AI） |

## 11. 建議 Demo 流程

### 情境 A：一般會員

1. Customer 登入。
2. 瀏覽與搜尋運動商品。
3. 開啟商品詳情。
4. 顯示 Local AI 相似商品與推薦理由。
5. 加入購物車並完成示範結帳。

### 情境 B：管理者

1. Admin 登入。
2. 查看營收、訂單、熱銷及低庫存 KPI。
3. 查看 Local AI Top-N 推薦、Similarity Score 及 latency。
4. 呼叫 Cloud LLM 產生本週營運摘要。
5. 詢問「哪些商品適合組合促銷？」並顯示回覆。

### 情境 C：技術比較收尾

- Baseline：穩定、零 API 成本、規則透明。
- Local AI：適合固定語意檢索，資料可留在本機。
- Cloud LLM：文字生成與推理較強，但依賴網路、額度與資料治理。

最後要說清楚的不是「哪個模型最大」，而是：

> **我們依任務特性選擇模型，讓成本、效能、隱私與展示穩定性取得平衡。**
