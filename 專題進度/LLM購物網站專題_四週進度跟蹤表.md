## 一、專案目標與範圍

本專題以陳仁千先前完成、部署於 Microsoft Azure 的購物網站為架構參考，重新以 Python、CSS 套件及 MongoDB 建置購物平台，並加入 LLM／語意模型功能。系統分為兩個主要使用情境：

1. **消費者端**：商品瀏覽、搜尋、個人化推薦、推薦理由。
2. **管理者端**：商品管理、銷售／行為摘要、LLM 營運洞察。

### MVP 範圍（四週內必須完成）

| 優先級 | 功能 | 驗收標準 |
|---|---|---|
| Must | 首頁、商品列表、商品詳情 | 可由 MongoDB 正確讀取並顯示商品 |
| Must | 商品搜尋與分類篩選 | 可依關鍵字及分類取得正確結果 |
| Must | AI／語意推薦 | 至少能依商品名稱、描述或類別推薦相似商品 |
| Must | 管理者商品 CRUD | 可新增、查詢、修改與下架商品 |
| Must | GitHub 協作流程 | 組員均由個人分支提交並透過 Pull Request 合併 |
| Must | 雲端展示網址 | 可由外部瀏覽器開啟並完成主要展示流程 |
| Should | LLM 推薦理由 | 以自然語言說明「為何推薦此商品」 |
| Should | 營運摘要 | 管理者可查看商品／模擬銷售摘要與 AI 建議 |
| Could | 會員偏好、購物車、完整訂單／金流 | 僅在 Must 全數完成後開發；金流不列本期必要範圍 |

## 二、專題名稱提案（2026-09-05 LINE 群組 2 決選）

| 比較項目 | 方案 A：VibeCart AI | 方案 B：InsightCart AI |
|---|---|---|
| 中文定位 | 智慧個人化推薦與營運分析購物平台 | 智慧購物洞察與決策支援平台 |
| 口號 | **懂你想買，更懂怎麼賣。** | **從每一次點擊，看見下一步商機。** |
| 命名原因 | 「Vibe」代表使用者偏好、情境與購物感受；品牌感較強，容易呈現消費者與商家的雙向價值。 | 「Insight」直接凸顯資料分析與商業洞察；專業感較強，適合強調 AI 應用與管理決策。 |
| 專題特色 | 個人化商品推薦、語意搜尋、推薦理由、管理者營運摘要；可拆分為 VibeCart（消費者）與 VibeInsight（管理者）兩個模組。 | 從搜尋、瀏覽與商品資料萃取洞察，提供推薦與管理建議；前台購物行為可回饋後台決策。 |
| 側重項目 | **消費者體驗 60%／營運洞察 40%** | **營運洞察 60%／消費者體驗 40%** |
| 展示優勢 | 畫面與故事性較活潑，適合成果展、品牌展示與一般觀眾理解。 | 技術與商業價值較明確，適合向老師說明 AI、資料及決策支援的整合。 |
| 主要風險 | 容易想做太多個人化功能，必須鎖定 MVP。 | 若沒有足夠交易資料，洞察功能須使用合理的模擬資料並清楚標示。 |

### 建議決策

- **首選：VibeCart AI**，較能同時容納消費者推薦與管理者分析，成果展示也較有記憶點。
- 若老師特別重視企業應用、資料分析及決策支援，改選 **InsightCart AI**。
- LINE 表決格式：`A VibeCart AI`／`B InsightCart AI`；平票時以「四週內較容易做出完整展示」為裁決原則。

### 分支與審查規則

1. `main`：只放可展示版本，禁止組員直接 Push。
2. `develop`：整合測試分支，各功能透過 Pull Request 合併。
3. `feature/*`：各組員日常開發分支；提交訊息建議採 `feat:`、`fix:`、`docs:`、`test:`。
4. 合併前至少 1 人 Review，並通過啟動測試、主要流程測試及敏感資訊檢查。
5. `.env`、MongoDB 密碼、API Key 不得提交；僅提交 `.env.example`。

### 建庫前仍需確認

- GitHub 倉庫擁有者：個人帳號或組織。
- 正式專題名稱與英文倉庫名稱。
- Public 或 Private。
- 另外兩位組員的 GitHub 帳號。
- 舊站程式碼是否有權移植；若不確定，只參考架構與流程，不複製原始碼。

## 八、部署平台選項

> MongoDB 建議統一使用 MongoDB Atlas；網站主機只承載 Flask 應用，連線字串放在平台環境變數。

| 平台 | 適合度 | 優點 | 注意事項 | 本專題建議 |
|---|:---:|---|---|---|
| **Render Web Service** | ★★★★★ | GitHub 串接與自動部署直覺；Flask 上線步驟短 | 免費／低價方案可能有休眠或資源限制；正式展示前需預熱 | **四週專題首選**，最快取得公開 Demo URL |
| **Azure App Service** | ★★★★☆ | 原舊站同平台；支援 Flask／Django／FastAPI；企業履歷價值高 | 設定與成本管理較多，需 Azure 訂閱與環境配置 | 若要延續陳仁千舊站經驗，列為首要備選 |
| **Google Cloud Run** | ★★★★☆ | 容器化、按需擴縮、可由原始碼部署 Python | 需理解 Container、專案計費與雲端權限 | 適合想凸顯雲端技術能力，但工期風險略高 |
| **Railway** | ★★★★☆ | Git 部署快速、環境變數管理簡單、適合 Prototype | 免費額度／計價政策須在決策日再次確認 | 可作 Render 的替代方案 |

### 部署決策建議

1. **預設採 Render＋MongoDB Atlas**：四週內交付風險最低。
2. 若陳仁千能提供現成 Azure 設定經驗或可用訂閱，改採 **Azure App Service＋MongoDB Atlas**。
3. 若課程明確要求 Docker／容器展示，再選 **Cloud Run＋MongoDB Atlas**。
4. 最晚 09/19 完成平台選型，09/25 前必須有測試網址；不可拖到封版週才首次部署。
